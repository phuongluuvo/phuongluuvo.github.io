# phuongluuvo.github.io

The personal and research-group website of **Assoc. Prof. Phuong Luu Vo** —
<https://phuongluuvo.me>.

Plain-text [jemdoc](http://jemdoc.jaboc.net/) sources are compiled to HTML by `build.py`,
mathematical notation is typeset in the browser by **MathJax 3**, and the result is published
with **GitHub Pages**.

**Where to look for what**

| I want to… | Read |
| --- | --- |
| edit the site, build it, publish it, or fix a problem | **[`guide.md`](guide.md)** — the manual, written for non-programmers |
| work on the repository as an AI coding agent | **[`AGENTS.md`](AGENTS.md)**, then `guide.md` §13 |
| understand the tooling, the vendored patches and CI | this file |

This file deliberately keeps **only** what `guide.md` does not cover. Everything operational
has a single home in `guide.md`, and is linked rather than repeated — see §7.

## 1. Repository layout

```
www/            the sources — the only place you normally edit
www/publications-extra.bib
                BibTeX for papers that are not in ORCID (see guide.md §9.2)
www/news-extra.txt
                your own announcements, for what is not a paper (see guide.md §9.1)
build.py        the build script (standard library only, Python 3.9+)
Makefile        optional one-word wrappers, including `make verify`
guide.md        the manual: build, edit, publish, troubleshoot, agent rules
AGENTS.md       entry point for AI coding agents
requirements.txt / environment.yml
                test dependencies (pip / conda) — keep the two in sync
tests/          44 checks that build the site and validate the result
tools/          helper scripts, including update_site.py (ORCID → Publications and News)
.github/        CI: build + deploy, and a rebuild-and-test job
_site/          GENERATED by build.py and gitignored. It does not exist until
                you build; GitHub Actions builds it and deploys it.
```

> The fully annotated tree, with a one-line purpose for every file, is in
> [`guide.md` §2](guide.md#2-folder-structure).

### The three rules

1. Edit sources in `www/` only — never a generated file. `build.py` writes everything into
   `_site/`, which is gitignored and rebuilt from scratch. Every generated page carries a
   `GENERATED FILE. DO NOT EDIT` comment in its `<head>`.
2. Run `python build.py` after every source change to verify it. Commit **sources only**; the
   published site is rebuilt from `www/` by CI.
3. Add, remove or rename a page only together with its line in `www/menu.jemdoc`.

## 2. Requirements

**Building** needs Python 3.9 or newer and nothing else: `build.py` is standard-library only.
jemdoc is vendored in `tools/` — do **not** `pip install jemdoc`.

**Testing** needs a few packages, listed once in [`requirements.txt`](requirements.txt) for pip
and once in [`environment.yml`](environment.yml) for conda. Keep the two lists in sync.

```bash
# conda
conda env create -f environment.yml      # creates the environment "vtlp"
conda activate vtlp

# or plain venv
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt    # Windows
.venv/bin/python   -m pip install -r requirements.txt      # macOS / Linux
```

A freshly created virtual environment contains none of the test packages, so `python -m pytest`
fails with `No module named pytest` until you run the install line.

## 3. Build, preview and test

```bash
python build.py           # rebuild the whole site into _site/
python build.py --serve   # build, then preview at http://localhost:8000
make verify               # rebuild and run all 44 checks
make update               # refresh Publications and News from ORCID, then build
```

`build.py` also takes `--out DIR` and `--clean`. The full command reference, the six steps the
build performs, the expected console output and the test breakdown are in
`guide.md` §4, §5 and §10.

## 4. The vendored jemdoc and its five local fixes

`tools/jemdoc` is the vendored [jemdoc+MathJax](https://github.com/wsshin/jemdoc_mathjax)
script (`jemdoc version 0.7.3`), with five small local fixes. They are all marked in the file
with a `LOCAL FIX` comment, so they are easy to re-apply if you ever update jemdoc from
upstream.

| # | Fix | Why it is needed |
| --- | --- | --- |
| 1 | `--version` decodes subprocess output as text | upstream crashes with `TypeError` on Python 3 |
| 2 | Internal links no longer get `target="blank"` | upstream forces **every** link into a new browser tab |
| 3 | `target="blank"` is written with escaped quotes | otherwise the "smart quotes" pass turns it into `target=&ldquo;blank&rdquo;` |
| 4 | `<img width="175">` instead of `<img width="175px">` | `175px` is not a valid HTML `width` and is silently ignored by browsers, which broke the portrait layout |
| 5 | Generated HTML is written with LF line endings | otherwise Windows produces CRLF, which is noisy in `git diff` |

`build.py` copes with CRLF in the *sources* as well, because jemdoc decides where a paragraph
ends by looking for a blank line, and a CRLF blank line is not recognised as a blank line. The
symptom is content being swallowed into the previous paragraph, so the build normalises the
line endings before jemdoc ever sees the files.

`tools/jemdoc` is GPL v3 and is the only file in this repository that is not written for this
site. `tools/make_placeholder_pdfs.py` (regenerates the placeholder CV in `www/files/`) and
`tools/README-jemdoc.md` (upstream attribution) are kept alongside it.

## 5. Continuous integration

`.github/workflows/pages.yml` runs on every push to `main`, and can be started by hand from the
**Actions** tab. It has two jobs:

| Job | What it does |
| --- | --- |
| `build` → `deploy` | refreshes the Publications page from ORCID (best effort), runs `python build.py --out _site`, uploads the folder, deploys it to GitHub Pages |
| `test` | a clean checkout, installs `requirements.txt`, runs `python -m pytest` |

The `test` job is deliberately **not** in the deploy job's `needs:`, so a CI hiccup cannot stop
the site being published. To make a failing test block deployment, add `needs: [build, test]`
to the `deploy` job.

**Required one-time setup:** **Settings** → **Pages** → **Build and deployment** → **Source** →
**GitHub Actions**. This is not optional — the generated HTML is no longer committed, so a
branch-based source would serve stale files. The branch-based fallback and the custom-domain
setup are in [`guide.md` §11](guide.md#11-deployment).

## 7. Where documentation belongs

There are exactly three documents. Each has one job, so that nothing has to be kept in sync by
hand:

| File | Audience | Contains |
| --- | --- | --- |
| `guide.md` | the site owner, contributors, agents | **all** operational material: build, edit, publish, troubleshoot, conventions |
| `README.md` | a developer joining the repository | tooling, the vendored patches, CI, licence — no duplicated how-to |
| `AGENTS.md` | AI coding agents | the hard rules; auto-loaded by the editor, so it stays short |

When you add a section, put it in the file whose job it is, and **link** to it from the others
instead of copying it. Duplicated procedures are how this repository gets out of step with
itself.
